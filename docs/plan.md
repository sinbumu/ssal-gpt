# 쌀-GPT 구현 설계

설계 기준일: 2026-11-07. 이 문서는 전체 목표를 설명한다. 실행 가능한 첫 MVP와 실제 검증 범위는 [구현 상태](implementation.md)를 참고한다.

## 1. 목적과 성공 기준

브라우저 화면을 보며 탐색·조건 이해·클릭·입력·완료 확인을 반복하는 에이전트를 만든다. 한국의 공개 이벤트 중 본인이 참여 가능한 기회를 찾고 실제 응모 흐름을 수행한다. 응모·당첨·수령·사용 결과를 기록해 운영비와 사람의 시간을 포함한 실익을 검증한다.

화면 기반 브라우저 조작은 제품의 핵심이다. 수집 API, 초안 생성과 수동 체크리스트만 있는 앱은 MVP 목표를 달성하지 못한 것으로 본다. 상세 구조는 [브라우저 에이전트 설계](browser-agent.md)를 따른다.

첫 경품 수령은 동작 사례이며 수익성의 증거로 일반화하지 않는다. 결과 미발표·발표 확인 불가를 낙첨으로 계산하지 않는다. 개발 시간과 일상 운영 시간을 별도로 기록한다.

## 2. 확정 요구사항

1. 공식 ChatGPT 로그인 / 플랜 사용량 연동과 OpenAI API 키 연동을 모두 첫 MVP에 포함한다.
2. 실행은 채팅 앱과 독립적이며 주기·시간대·동시성·작업량·예산을 설정으로 조정한다.
3. 처음 필요한 서비스에만 가입·로그인·권한 승인을 요청한다. 전 플랫폼 계정 가입을 초기 설치 조건으로 만들지 않는다.
4. 공개 검색·홈페이지·사용자 제공 자료로 탐색을 시작할 수 있어야 한다.
5. 응모를 개별 행동으로 분해하고 자동/사용자 승인/사용자 직접 수행/미지원 상태를 표시한다.
6. 사용자 개입 대기 중에도 독립적인 다른 이벤트 작업은 진행한다.
7. 참가 제한은 계정 수가 아닌 이벤트 규칙의 참가자 단위로 검사한다.
8. 개인정보·인증정보·쿠폰은 공개 저장소와 분리한다.
9. 전용 Chromium에서 스크린샷 관찰·스크롤·클릭·입력·다시 관찰하는 실행 루프를 첫 MVP에 포함한다.
10. ChatGPT 로그인 경로에서도 화면 이해와 로컬 브라우저 도구 실행이 함께 동작해야 한다. 네이티브 Computer Use 도구가 없어도 앱 자체 실행기로 구현한다.
11. 서비스 API와 브라우저 UI는 별개 실행 경로다. API 엔드포인트 부재만으로 UI 행동을 수동 전용으로 분류하지 않는다.

## 3. 세 종류의 연결

### AI 연결

- ChatGPT OAuth: 공식 앱별 등록·권한 동의 흐름을 사용한다. 로그인 성공 후 플랜 사용 권한과 실제 모델 호출 가능 여부를 별도로 검증한다.
- OpenAI API 키: 사용자가 선택한 API 조직·프로젝트의 과금 경로를 사용한다.
- 둘은 독립된 제공자다. 인증 실패·사용량 한도 발생 시 유료 경로로 자동 전환하지 않는다.
- ChatGPT 연동이 기존 ChatGPT 대화, SNS 로그인, 이 개발 환경의 플러그인과 도구를 자동 제공한다고 가정하지 않는다.

### SNS·폼 연결

- 화면 조작을 기본 실행 경로로 두고, 검증된 공식 API는 보조 경로로 사용할 수 있다.
- 기본은 앱 전용 Chromium 지속 프로필이다. 필요한 사이트에서 사용자가 직접 최초 로그인한다.
- 기존 브라우저는 사용자가 선택한 프로필·탭만 연결하는 별도 모드로 확장한다. 디버깅 접근이나 확장 설치가 필요하면 사전 연결 단계로 명확하게 다룬다.
- 로그인 상태 재사용은 기술적 기능이다. 해당 서비스에 대한 자동 접근·수집·제출 허용을 뜻하지 않는다.
- 비밀번호·OTP·CAPTCHA·복구·약관 동의는 사용자에게 맡긴다. 세션 만료 시 해당 연결만 멈춘다.
- 일반 브라우저의 기존 쿠키·로그인을 몰래 가져오지 않는다. 다른 기기·서버로 이동할 때 로그인 유지가 보장되지 않는다.

### 개인 참여 정보

- 사용자가 명시한 이름, 연락처, 지역, 응모에 필요한 자격과 실제 선호만 저장한다.
- 제출 전 이벤트 주최자·최종 도메인·전송 항목을 보여준다. 새 필드·목적·수신자가 생기면 기존 승인과 분리한다.
- 연락처를 모델에 보낼 필요 없이 필드 자리표시자를 해석한 후 로컬에서 값을 채울 수 있도록 한다.
- 마케팅 수신 등 선택 동의를 자동 체크하지 않는다.

## 4. 실행 구조

```text
Scheduler → Persistent job queue → Worker
                                  ├─ Task goal / eligibility / authorization
                                  ├─ Browser agent loop
                                  │    Observe: screenshot + visible element refs
                                  │       ↓
                                  │    Decide: ChatGPT OAuth / OpenAI API
                                  │       ↓
                                  │    Execute: scroll / click / type / upload
                                  │       ↓
                                  │    Verify: fresh observation → next decision
                                  ├─ Pause / manual takeover / recovery
                                  ├─ Optional search / service API adapters
                                  └─ Result / claim tracking and usage records
                         SQLite + protected local credential/profile storage
```

AI가 판단에 필요한 순간만 호출한다. 날짜 비교, 예산·작업량 검사, 상태 전이, 중복 제거, 재시도는 코드로 처리한다. 공식 ChatGPT 연동의 `background` 필드 지원 여부와 앱 자체의 스케줄 실행은 별개다. 장기 실행은 이 앱의 프로세스가 담당한다.

### 기술 선택 제안

TypeScript + Node.js + SQLite + Playwright + 로컬 작업 화면을 기본 구현 제안으로 둔다. Playwright는 Chromium 화면 관찰과 마우스·키보드 실행을 담당하고 AI는 목표와 현재 관측을 바탕으로 행동을 선택한다. 화면과 DOM/접근성 정보를 함께 활용하되, 화면을 모델이 실제로 이해하고 좌표 행동을 수행하는 경로도 반드시 구현한다. 첫 MVP는 이 구성을 채택했다. 실제 의존성은 package.json과 package-lock.json에 고정한다.

운영은 로컬 PC에서 시작한다. PC가 잠들거나 프로세스가 종료되면 실행이 중단되므로, 작업은 재시작 후 이어져야 한다. 이후 사용자 소유 상시 실행 환경을 검토한다. 공개 저장소의 CI에는 개인 SNS 세션이나 쿠폰을 넣지 않는다.

## 5. 이벤트와 행동 모델

이벤트는 필요한 행동들의 의존 관계로 표현한다. 예: 자격 확인 → 요구된 SNS 행동 → 실제 인증샷 준비 → 폼 작성 → 제출 확인. 각 행동은 브라우저 에이전트가 수행하거나 실제로 사용자 개입이 필요한 경우 대기한다. 단순 클릭·입력을 처음부터 수동 작업으로 고정하지 않는다.

행동 종류:

- `read_source`, `answer_quiz`, `draft_comment`
- `like`, `follow`, `subscribe`, `post_comment`, `share_post`
- `fill_form`, `upload_evidence`, `submit_form`
- `check_result`, `claim_reward`, `record_redemption`

각 행동에 아래 정보를 저장한다.

- 원문 조건과 근거 위치, 필수/선택 여부, 선행 행동
- 플랫폼·필요 계정·지원 어댑터와 허용 근거
- 실행 모드: `automatic`, `approval_required`, `manual`, `unsupported`
- 전송 데이터 항목, 대상 URL·도메인, 게시할 정확한 내용
- 완료 증거와 관측 시각; 사용자 완료 확인은 시스템 검증과 구분

글의 조건이 바뀌거나 대상·답변·개인정보가 바뀌면 해당 승인을 무효화한다. 한 이벤트의 승인이 다른 이벤트나 데이터 전송까지 확대되지 않게 한다. 필수 행동이 미지원이면 자동 참여 가능으로 표시하지 않는다.

### 기록할 엔터티

- `Event`: 대표 URL, 여러 출처 URL, 주최자, 일정, 경품, 선정 방식, 참가 제한, 근거, 신뢰도
- `Participant`: 로컬 참가자 식별자와 명시된 자격 정보. 인증 토큰과 분리
- `Connection`: 제공자, 로컬 비밀정보 참조, 허용 범위, 유효 상태
- `Task`: 행동, 의존 관계, 상태, 재시도 정책, 시간·사용량
- `Observation` / `BrowserAction`: 브라우저·탭·관측 ID, 화면 좌표 체계, 관측 근거, 실행한 도구, 전후 상태와 검증 결과. 모델의 숨은 사고과정은 저장하지 않음
- `Approval`: 이벤트·행동·대상·데이터·내용에 묶인 승인과 만료
- `Submission`: 중복 방지 키, 요청·응답 증거, 확인된 완료 시각
- `Outcome`: 발표 대기/당첨/낙첨/확인 불가, 근거와 수령 기한
- `Reward`: 수령 여부, 만료일, 액면가, 실제 사용 가치 또는 판매대금

같은 캠페인의 여러 SNS 게시물은 하나로 묶는다. 재응모 허용이 명확한 이벤트만 라운드/허용 기간을 중복 방지 키에 포함한다.

## 6. 복구와 비용

- 타임아웃 뒤 제출 여부를 모르면 `submission_unknown`으로 기록하고 확인 작업으로 전환한다. 재제출을 자동으로 반복하지 않는다.
- 로그인 재확인이 필요하면 해당 연결을 `needs_login`으로 바꾸고 다른 독립 작업은 계속한다.
- CAPTCHA·본인인증 등은 `needs_user`로 전환한다. 우회하지 않는다.
- 일시적 서버 오류는 제한된 횟수의 지연 재시도, 권한·자격·과금 오류는 원인별 중지로 처리한다.
- 대기 중 반복적인 모델 호출을 하지 않는다. 같은 원문 해시는 결과를 재사용하고 변경 시 재분석한다.
- 제공자별 토큰·도구 사용량, 관측 가능한 비용과 추정값을 구분해 저장한다. 주간 한도나 API 금액을 임의로 크레딧과 환산하지 않는다.
- 작업별 시간·호출 횟수·행동 횟수 및 일별 예산을 앱에서 제한한다. 공급자가 지원하지 않는 출력 제한 필드에 의존하지 않는다.
- 발표 확인 실패는 낙첨이 아니다. 개인정보와 쿠폰은 로그에서 마스킹한다.
- 사용자 수동 조작·재시작·화면 변경 후에는 기존 클릭 좌표를 재생하지 않고 현재 화면을 다시 관찰한다.
- 프로필/탭의 쓰기 작업은 잠금으로 직렬화한다. 사람이 제어권을 가져가면 예약된 브라우저 행동을 취소한다.

## 7. 구현 순서와 완료 조건

2026-11-09 진행 현황: 아래는 최초 완료 조건을 유지한 계획이다. M0의 실제 API 호출, M1의 실사이트 SNS 행동, M2의 플랫폼별 실서비스/커스텀 위젯 검증은 남아 있다. 예약·사용량·작업별 탭·공식 발표 읽기·사용자 확인 결과/쿠폰 관리의 M3 구현과 합성 검증은 추가됐다. 실제 경품 수령·장기 운영은 아직 검증하지 않았다. 현재 검증 증거는 `implementation.md`와 README 기능표를 따른다.


### M0: 인증 두 경로 + 화면 기반 브라우저 실행 — 첫 필수 단계

- 공식 ChatGPT 연결 등록·권한 검사·모델 조회·실제 추론 성공·토큰 갱신 처리.
- API 키 경로로 같은 브라우저 작업을 실행할 수 있도록 제공자를 분리. 사용자가 선택한 경로를 명확히 표시.
- 전용 Chromium을 열고 화면을 AI에 전달한 뒤 스크롤·클릭·입력·다시 관찰하는 실제 루프를 구현.
- 합성 이벤트 화면에서 팝업·스크롤 아래 조건·퀴즈·응모 폼·완료 확인을 수행. 고정된 페이지별 동작 스크립트만으로 성공 처리하지 않음.
- 레이아웃 변화, 수동 개입, 성공 응답 유실을 포함한 평가. 화면 좌표 행동과 요소 참조 행동 모두 확인.
- 한도/권한 실패 시 중지하고 유료 경로로 넘어가지 않는지 확인.
- 실행 기록을 저장하고 앱 종료 후 이어가기.
- 제공자별 호출에 필요한 도구만 구현한다. API 호출 도구나 실제 인증이 없으면 미검증 상태를 표시한다.

### M1: 브라우저 탐색·조건 이해와 SNS 행동 검증

- 브라우저에서 검색·목록 스크롤·게시물 열기·본문 확장·여러 탭 이동을 수행. 사용자 제공 자료와 검색 API도 보조 입력으로 지원.
- 마감, 필수 과제, 자격, 경품, 발표 방식 추출과 근거 표시.
- 댓글·퀴즈 작성, 중복 제거, 발표 일정. 클릭·텍스트 입력·게시 확인은 브라우저 실행기 대상 행동으로 구현.
- 실제 사이트는 접근 조건·계정·사용자 권한을 확인한 범위에서 검증한다. 검증된 행동과 아직 검증하지 않은 행동을 구분해 표시.
- 검수 예제로 누락·날짜 해석·교차 채널 중복을 평가.

### M2: 여러 단계 응모와 증거

- 자체 테스트용 폼에서 단답·선택·다중 선택·실제 증거 파일 첨부를 검증.
- 허용과 구현 경로가 확인된 실서비스로 확장. 사이트별 API 대신 화면 관찰과 도구 실행으로 필드를 처리하고, 필요한 사이트별 힌트만 추가.
- 제출 직전 정확한 내용·대상·개인정보를 검토하고 완료 증거 확인.
- 재시작·타임아웃·중복 클릭이 이중 제출을 만들지 않는지 테스트.

### M3: 주기 실행과 결과·경품 관리

- 검색/결과 확인 일정, 사람 개입 대기열, 연결 만료 알림.
- 허용된 출처의 발표 확인, 또는 사용자의 공식 발표/DM 확인 결과 입력.
- 당첨 확인, 수령 기한과 쿠폰 만료, 실제 실현 가치 기록.
- 사람이 들인 시간, 누락/무효, 비용과 성과 보고.

### 이후

기존 사용자 브라우저 연결, 검증된 플랫폼별 실행 힌트, 승인된 반복 작업, 허용된 창작 과제, 사용자가 소유한 상시 실행 환경을 순서대로 검토한다. 브라우저 에이전트 자체를 후속 선택 기능으로 미루지 않는다. 모든 SNS의 모든 이벤트가 무인 실행된다는 보장은 하지 않는다.

## 8. 실사용 피드백: 왕복 최소화와 자율 응답

2026-11-08 실서비스 다단계 설문 테스트에서 나온 제품 요구사항이다. 아래는 개발할 목표이며, 현재 구현된 기능으로 간주하지 않는다. 특히 **추천 답변 사전 설정과 자동 적용은 핵심 우선순위**다.

### 질문을 모으고 대시보드에서 답하기

- 문항마다 대화 왕복을 만들지 않는다. 현재 페이지에서 볼 수 있는 질문·선택지·필수 여부·선택 개수를 먼저 모아 한 번에 요청한다.
- 최종 제품의 기본 입력 장소는 로컬 대시보드의 답변 검토 화면으로 한다. 선택형, 다중 선택, 평가 표, 자유 응답을 실제 컨트롤로 표시하고 한 번에 저장·적용할 수 있게 한다. 채팅은 선택적 알림/입력 경로다.
- 이미 제공한 답변과 재사용 가능한 선호는 미리 채우고, 새로 필요한 답변과 충돌만 눈에 띄게 표시한다. 같은 답변을 반복해서 묻지 않는다.
- 사용자가 직접 설문을 빠르게 입력하는 편이 나은 경우에는 브라우저를 넘기고 현재 화면에서 이어받는 경로도 유지한다.

### 여러 페이지에서도 개입·대기 시간을 줄이기

- 페이지 안에서 읽을 수 있는 질문은 일괄 수집한다. 뒤 문항이 이전 답변 전송 뒤에만 나타나는 설문은 그 의존 관계를 유지한다. 미래 질문을 알아내기 위해 임의 응답을 보내거나 진행 중인 POST 폼을 다시 열지 않는다.
- 사전 답변 프로필, 질문 의미에 따른 답변 재사용, 분기별 답변 정책을 통해 다음 페이지에서도 새 판단이 필요한 문항만 요청한다.
- 여러 입력을 한 번의 계획으로 결정하고 로컬 실행기가 순차 적용하는 방식을 검토한다. 각 동작은 실제 선택 상태·관측 유효성을 검사하고, 조건부 문항이나 화면 변경이 생기면 남은 계획을 버리고 재관찰한다.
- 일반 선택·스크롤까지 매번 장시간 모델 추론을 거치는 비용과, 사람 답변 대기 시간을 별도로 줄인다. 사용자에게 이미 승인받은 범위의 일상 입력 때문에 재승인을 만들지 않는다.
- 긴 설문에서 판단 한도를 소진할 때는 대시보드에서 남은 예산을 확인하고 추가할 수 있도록 개선한다. 누적 사용량·진행 중 폼·승인·제출 상태를 보존하며, 개발자가 로컬 데이터를 수정해야 이어갈 수 있는 상태를 없앤다.
- 수집 단계에서도 예상 질문 수, 개인 의견 문항 비중, 예상 사람 개입 시간으로 이벤트를 평가한다. 경품 규모뿐 아니라 완료에 드는 사람 시간을 추천 순위에 반영한다.

### 추천 답변과 사전 설정에 따른 자동 적용 — 핵심 우선순위

- 각 문항에 추천 답변과 짧은 근거를 제공하고, 대시보드에 **추천 답변 모두 선택**을 둔다. 사용자는 적용 전에 일부를 수정할 수 있다.
- **허용한 범위의 추천 답변 자동 적용**을 사전 설정할 수 있게 한다. 설정된 질문 유형·이벤트·사용자 프로필 범위 안에서는 매번 질문하지 않고 진행한다.
- 답변의 출처를 구분한다: 사용자가 확인한 사실/경험, 명시한 선호, 공개 근거가 있는 퀴즈 정답, 사용자가 정한 기본 선택 규칙. 과거의 특정 문항 답을 새로운 경험이나 모든 만족도 문항의 답으로 자동 확대하지 않는다.
- 경험·자격 같은 사실을 모를 때 지어내는 방식 대신, 해당 사실을 프로필에서 한 번 확인하거나 사용자에게 요청한다. 추천을 허용했다는 설정과 새로운 개인정보·동의의 허용은 구분한다.
- 설정 화면에는 적용 범위, 예외, 만료/수정 방법을 제공하고 실행 기록에는 자동 적용한 답변과 적용 이유를 남긴다. 추천은 당첨 확률을 높인다는 보장이 아니다.

### 불일치와 예외의 중요도에 따른 처리

- 안내는 다중 선택인데 실제 UI는 단일 선택인 경우처럼 사소한 모순을 매번 질문하지 않는다. 해당 문항의 의미, 되돌릴 수 있는지, 사용자 의도와 사전 규칙으로 해소 가능한지에 따라 경로를 정한다.
- 낮은 중요도의 선호 선택이고 사용자 우선순위가 있다면 가장 높은 항목을 선택한 뒤 기록한다. 예를 들어 세 항목을 원했지만 하나만 가능하다면 사용자가 정해둔 단일 선택 대체 규칙을 적용한다. 나열 순서를 우선순위로 쓸지는 설정으로 명시한다.
- 선호 순위가 없을 때도 사용자가 허용한 자율 선택 범위에 해당하면 추천 기준으로 하나를 고르고 사후 요약한다. 그 범위를 벗어나거나 결과에 큰 차이가 있으면 질문한다.
- 개인정보/동의 범위 변경, 자격 판단, 비용 발생, 공개 게시 내용 변경, 제출 결과 불명은 별도 검토 경로를 유지한다. 낮은 중요도의 예외와 같은 규칙으로 처리하지 않는다.

### SNS 사전 연결과 기본 응모 정보

- 대시보드 연결 설정에 Instagram 등 지원하는 SNS별 로그인/연결 버튼을 미리 제공한다. 필요한 이벤트가 나타나기 전에도 사용자가 전용 지속 브라우저에서 로그인해 둘 수 있게 한다.
- ChatGPT 연결과 SNS 연결은 화면에서 구분하고, 각 SNS에 로그인 상태 확인·다시 연결·연결 해제를 제공한다. 최초 로그인·MFA는 사용자가 처리하며 이후 동일한 허용 프로필에서 로그인 상태를 재사용한다. 세션 만료가 감지되면 해당 연결만 갱신하도록 안내한다.
- 대시보드에 참여자 기본 정보 입력 화면을 둔다. 이름·이메일·전화번호 등 자주 요구되는 정보와 사용자 답변 프로필을 미리 관리하고 필요할 때 기본값으로 사용한다.
- 사용자가 설정한 필드·용도·수신 대상 범위에서는 로컬에서 값을 채우고 매번 같은 정보를 다시 묻지 않는다. 새로운 범위가 생긴 경우에만 추가 검토로 보낸다.
- 개인정보 값은 보호된 로컬 저장소에서 관리하고 공개 저장소·일반 로그·모델 문맥과 분리한다. 모델에는 필드 종류와 로컬 참조만 전달하고, 실제 값 대입은 실행기가 처리한다. 사용자는 기본값 수정·삭제와 적용 내역 확인이 가능해야 한다.
- 개인정보 자동 입력과 선택 동의는 별도 설정으로 다룬다. 계정 연결 및 기본 정보 저장만으로 마케팅 동의까지 포함하지 않는다.

### 구현 순서와 검증 기준

1. 페이지 단위 질문 묶음과 대시보드 일괄 답변 UI.
2. SNS 사전 연결·상태 확인과 기본 응모 정보 저장/재사용.
3. 재사용 답변 프로필, 추천 답변 검토/전체 선택, 자동 적용 범위 설정. 핵심 우선순위로 기본 정보 재사용과 함께 설계한다.
4. 중요도별 예외 처리, 중간 입력의 묶음 실행, 분기 설문 처리 최적화.

반복 평가에서는 사람에게 질문한 횟수, 사용자 직접 조작 시간, 모델 대기 시간, 전체 완료 시간, 자동 적용률, 수정률, 잘못된 답변/중복 제출을 함께 기록한다. 최적화 전후에 같은 합성 분기 설문으로 비교하고, 실제 응모는 별도 사례로 기록한다. 목표 수치는 기준 측정 뒤 정한다.

## 9. 다음 버전의 자율 운영 설계

목표는 사용자가 운영 기준과 연결·기본 정보를 설정하면, 에이전트가 참여할 기회를 고르고 답변·행동을 계획하며 예외를 해결해 결과까지 보고하는 것이다. 개발 대화에서 사람이 수행한 응답 재사용, 구체적 행동 검토, 복구 판단을 제품 내부의 명시적 기능으로 옮긴다. 프로필·위임, 네이티브 폼의 답변 재사용/묶음 실행, 확인함, 제한된 복구를 연결한 구현이 추가되었다. 아래 전체 설계가 모두 완료된 것은 아니며, 현재 범위와 검증 결과는 [구현 상태](implementation.md)를 기준으로 한다.

### 현재 병목과 바꿀 책임

- 현재는 모델이 관찰마다 동작 하나를 반환한다. 스크롤·라디오 선택 같은 일상 동작도 판단 호출을 소모한다. 다음 구조에서는 모델이 의미를 해석하고 제한된 행동 묶음을 계획하며 실행기는 실제 입력·검증을 처리한다.
- 현재 `userContext`는 누적 문자열이고, 질문·답변·근거·위임 범위가 별도 데이터로 관리되지 않는다. 기존 답변을 관련 문항에 재사용할 책임을 질문 해석기와 답변 정책에 둔다.
- 현재 `actionPolicy`는 개인정보 입력을 차단하고 대부분의 체크박스·새 문구·제출을 개별 검토로 보낸다. 대시보드에 저장 폼만 붙여서는 자율 입력이 되지 않는다. 확인된 프로필 참조와 범위가 있는 위임을 검사하는 실행 경로가 함께 필요하다.
- 현재 완료 판정은 특정 문구 목록에 크게 의존한다. 새 사이트의 완료 표현을 해석하되, 실제 제출 시도와 새 화면 근거를 함께 검사하도록 개선한다.
- 개발자가 상태 데이터나 실행 한도를 직접 고쳐야 이어지는 경로는 제품의 복구 기능과 예산 관리로 대체한다.

### 운영 기준과 기억

처음 설정할 내용은 선호 경품·예산·사람에게 질문할 수 있는 범위·제외 조건·정보 사용 범위·공개 게시 정책이다. 클릭별 승인은 이 운영 기준으로 허용되지 않은 변경에 집중한다. 사용자 설정은 에이전트나 페이지가 스스로 확대하지 못한다.

| 기억 종류 | 보관할 내용 | 재사용 기준 |
| --- | --- | --- |
| 기본 사실 | 이름·연락처 등 프로필, 확인된 참가 자격 | 출처·확인 시점·허용 필드/수신 대상/목적 검사 |
| 사용자 선호 | 관심 분야, 원하는 혜택, 항목 우선순위 | 현재 질문 의미와 관련된 경우 사용 |
| 위임 정책 | 추천 답변 자동 적용, 일반 평가 기준, 사소한 충돌의 대체 규칙 | 적용 질문 유형·이벤트/사이트 범위·만료·정책 버전 검사 |
| 작업 내 기억 | 이미 제출한 답, 분기, 현재 단계, 완료 조건 | 해당 응모 안에서 일관성 유지 |
| 검증된 작업 요령 | 폼의 구조, 필요한 과제, 작동한 조작 방식 | 현재 화면의 전제조건을 다시 확인한 뒤 재사용 |

특정 이벤트에 준 평가 기준을 모든 사이트의 영구 성향으로 바꾸지 않는다. 프로필 변경·위임 철회 시 영향을 받는 미실행 계획만 무효화한다. 개인정보 원문은 로컬에서 참조를 값으로 바꾸고 모델에 전달하는 문맥과 분리한다. 웹페이지의 문구나 에이전트 추측을 사용자가 확인한 사실로 승격하지 않는다.

### 질문 해석 → 답변 계획 → 묶음 실행

1. 에이전트가 화면과 보이는 요소를 함께 읽어 현재 페이지의 문항을 구조화한다. 질문 본문, 선택지, 필수 여부, 단일/다중 선택, 최대 개수, 실제 컨트롤, 화면 근거를 연결한다. 안내와 UI가 다르면 두 정보를 보존한다.
2. 질문을 사실·선호·일반 평가·근거 있는 퀴즈·자유 서술·동의 등으로 구분한다. 답변 후보마다 근거가 프로필인지, 사용자 답변인지, 위임 규칙인지, 공개 자료인지 기록한다.
3. 정책 범위 안에서 충분히 근거가 있는 답은 자동 적용한다. 중요한 정보가 부족한 문항은 대시보드 확인함에 모은다. 의미가 비슷해도 긍정/부정 문항, 선택지 순서, 시점·서비스 범위가 다르면 그대로 복사하지 않는다.
4. 모델은 `문항 식별 → 선택/입력할 내용 → 기대 상태 → 멈출 조건`으로 이루어진 제한된 계획을 반환한다. 임의 JavaScript나 자유 형식 코드를 실행 계획으로 받지 않는다.
5. 로컬 실행기는 각 동작 직전에 현재 요소를 다시 연결하고 답변 상태를 확인한다. 오래된 좌표·요소 ref 묶음을 재생하지 않는다. 조건부 문항 출현, 선택 해제, 필수 항목 변경이 있으면 남은 계획을 취소하고 재관찰한다.
6. 페이지 답변 전체를 검증한 뒤 중간 전송을 수행한다. 전송은 해당 데이터·대상·목적을 포함하는 위임으로 판단한다. 최종 제출은 별도 단계로 다루며 허용 범위 안이라면 자동 진행할 수 있다.

스크린샷은 페이지를 이해하고 예상과 다른 결과를 판별하는 관측 수단으로 유지한다. 일상 입력의 매 단계마다 비싼 의미 추론을 반복할 필요는 없지만, 관측·상태 확인까지 생략하는 것은 아니다. 페이지별 한 번의 계획으로 처리하는 방식을 우선 검증하고 실제 분기나 실패 때 추가 추론한다.

미래 문항이 이전 답변 전송 뒤에만 공개되는 설문은 전체 질문을 처음부터 모을 수 없다. 이런 경우 다음 페이지에서도 프로필과 위임을 재사용해 추가 질문을 줄인다. 미공개 질문을 찾기 위해 임의 응답을 제출하거나 POST 기반 진행 화면을 다시 열지 않는다.

### 질문할지, 스스로 처리할지, 포기할지

| 상황 | 우선 처리 | 사용자 개입 조건 |
| --- | --- | --- |
| 최대 3개 안내지만 실제 단일 선택 | 저장된 우선순위 또는 허용된 대체 규칙으로 하나 선택, 처리 이유 기록 | 우선순위에 따라 자격·공개 내용·결과가 크게 달라지는데 위임이 없을 때 |
| 버튼/라벨 조작 실패 | 새 관찰 → 보이는 연결 label/input → 화면 좌표 등 제한된 대안 검토 | 정해진 복구 예산 소진, 로그인 등 직접 조작 필요 |
| 이전 답과 의미가 같은 질문 | 질문의 대상·시점·부정 표현을 확인해 답변 재사용 | 의미 차이가 실제 답을 바꿀 수 있을 때 |
| 새 실제 경험·자격 질문 | 확인된 사실 조회, 관련 문항과 함께 질문 | 해당 사실이 없고 진행에 필요할 때 |
| 허용되지 않은 정보 전송·비용·새 동의 | 해당 단계 대기, 정확한 변경 내용 표시 | 기존 운영 기준에 포함되지 않을 때 |
| 제출 후 결과가 불명확함 | 현재 결과 화면·접수 기록을 읽어 확인 | 읽기만으로 확인되지 않을 때; 재제출로 확인하지 않음 |
| 노력 대비 가치가 낮거나 반복 실패 | 중단·제외하고 다른 후보를 검토 | 사용자가 지정한 우선 이벤트를 포기해야 할 때 등 정책 밖 판단 |

경로 결정에는 불확실성뿐 아니라 잘못 선택했을 때의 영향, 되돌릴 수 있는지, 사용자에게 질문하는 비용을 함께 사용한다. 모델이 스스로 붙인 확신 점수 하나로 허용 범위를 정하지 않는다. 저위험 예외의 자율 처리와 검토가 필요한 사실·전송을 구분한다.

### 기회 선택과 지속 운영

- 탐색 결과를 모두 응모하지 않는다. 참가 자격, 연결 준비, 과제 유형, 예상 사람 개입 시간, 실행 시간/사용량, 선호 경품, 마감을 보고 착수·보류·제외를 결정한다.
- 상세 과제를 열어 보니 부담이 큰 경우 처음 순위를 다시 계산하고 포기할 수 있게 한다. 이미 쓴 시간이 아깝다는 이유로 계속 진행하지 않는다.
- 참가 인원이나 추첨 확률이 없으면 이를 만들어 기대 수익을 계산하지 않는다. 처음에는 관측 가능한 경품·노력·개입 비용으로 우선순위를 정하고, 실제 결과가 쌓이면 출처/유형별 운영 성과를 비교한다.
- 사람이 답변 중인 POST 폼은 해당 탭/프로필의 소유권과 함께 보존한다. 독립적인 탐색은 별도 읽기 컨텍스트로 진행할 수 있지만 대기 폼을 다른 작업의 화면으로 덮어쓰지 않는다. 세션을 잃은 경우 복구 가능 여부부터 판단한다.
- SNS 연결 버튼은 실제 전용 브라우저 로그인, 연결 상태 확인, 재연결로 이어져야 한다. 최초 대상은 한 서비스로 좁혀 세션 재사용과 허용된 과제를 실제 검증한다.
- 완료 후 발표일과 공식 확인 경로를 기록하고, 이후 발표 확인·필요 수령 절차·쿠폰 보관으로 이어지는 작업을 만든다. 예약 실행과 메시지/메일 접근은 사용자가 설정한 연결과 범위 안에서 별도 구현한다.

### 완료 판단과 피드백

완료 판정은 명시적인 제출 시도, 새 결과 화면, 사이트의 완료 표현 또는 접수번호를 함께 판단한다. 제출 전에 있던 감사 문구, 중간 페이지 이동, ‘완료되지 않았다’ 같은 부정 표현을 구분한다. 모델의 의미 해석은 정확한 화면 인용·URL·스크린샷과 연결하고 실행기가 제출 이력·관측 일관성을 검사한다. 확인 가능한 완료, 추가 검증 필요, 실패를 구분한다.

사용자가 고친 답변은 적용 범위를 확인한 규칙으로 저장하고, 성공한 작업 요령은 검증 사례로 남긴다. 선택 하나를 고쳤다는 이유로 모든 사이트의 프로필을 자동 변경하지 않는다. 운영 에이전트가 자신의 실행 코드나 권한을 즉석 수정하는 방식은 초기 자율화 범위에 넣지 않는다.

### 대시보드와 다음 구현 단위

대시보드는 계정·기본 정보, 운영 기준, 확인함, 진행/결과의 네 영역으로 구성한다. 확인함에는 해결하지 못한 문항과 제안 답변·근거를 모으고, 한 번에 수정/적용·작업 재개를 제공한다. 일상적으로는 완료·제외·대기 결과 요약을 보여주고 상세 클릭 기록은 펼쳐 볼 수 있게 한다.

실사용 추가 피드백에 따라 완료한 응모는 수집 후보·실행 로그와 별도 목록으로 제공한다. 경품, 접수 확인 시각, 발표 안내, 완료 증거를 직접 찾을 수 있어야 한다. 최종 검토의 기본 표현은 질문/답변 목록이며 원본 JSON은 상세 보기에 둔다. 발표 결과와 수령 여부는 응모 완료와 구분한다.

다음 개발은 **기본 정보/위임 → 질문 구조화와 답변 재사용 → 페이지별 묶음 실행 → 확인함과 복구 → 실제 완료 증거**를 연결한 한 개의 수직 기능으로 진행한다. 각 단계가 연결되기 전에는 대시보드에 저장 폼이 생긴 것만으로 자율 응모가 구현됐다고 표시하지 않는다. 기존 TypeScript/SQLite/브라우저 프로세스 안에서 책임을 나누며 별도의 범용 다중 에이전트 프레임워크를 먼저 도입하지 않는다.

그 다음 기회 선택·중단 판단과 한 SNS의 연결/실행을 검증하고, 마지막으로 예약 운영·발표/수령 관리를 붙인다. 여러 플랫폼 지원 확장과 자율성 검증을 동시에 크게 벌리지 않는다.

완료 조건은 처음 설정한 정보·위임으로 처리 가능한 새로운 합성 분기 폼을 **개발자의 중간 지시나 데이터 수정 없이** 끝내는 것이다. 재사용 가능한 답을 다시 묻지 않고, 필요한 질문은 묶어서 요청하며, 화면 변경·단일/다중 선택 충돌·새 완료 표현을 처리해야 한다. 잘못된 사실 생성, 허용 범위 밖 전송, 중복 제출은 성공률과 별도로 실패로 센다.

검증 시에는 전체 경과 시간에서 사용자 응답 대기·모델 추론·브라우저 실행·검토 갱신·복구 시간을 분리한다. 모델 호출 수, 사람 개입 횟수/시간, 예외 자율 해결률, 프로필/답변 수정률, 완료 증거 정확도를 함께 기록한다. 이미 응모한 실이벤트를 다시 제출하지 않고 합성 시나리오와 미참여 이벤트로 검증한다. 자율성은 동일 문구의 반복 실행뿐 아니라 처음 보는 문항·배치에서도 확인한다.

## 10. 추가 피드백: 동의 위임 3단계

2026-11-09 실서비스 응모 중 나온 요구사항이다. **첫 구현과 합성 검증을 반영했다. 기존 사용자 설정은 1단계로 유지하며 자동 동의를 임의로 켜지 않는다.** 대시보드 `05 프로필·위임`에 동의 전용 설정을 두고, 답변 추천·개인정보 자동 입력·최종 제출 정책과 분리한다. 단순한 ‘모두 동의’ 옵션은 만들지 않는다. 현재 지원 경계와 실제 검증 범위는 [구현 상태](implementation.md)의 동의 위임 항목을 따른다.

| 단계 | 자동 처리 범위 | 확인함으로 보내는 경우 |
| --- | --- | --- |
| 1. 모든 동의 직접 확인 — 기본값 | 동의 내용을 정리하고 사용자 선택을 기다림 | 모든 동의 |
| 2. 사전 허용한 통상 동의 | 허용한 프로필 항목을 응모·경품 안내 목적으로 사용하고, 수신자·보관 기간 등 사용자가 정한 조건을 충족하는 동의 | 새 항목·목적·수신자, 허용 기간 초과, 불명확한 안내 |
| 3. 범위 안에서 에이전트 판단 | 프로필 항목과 정확히 일치하지 않아도, 미리 허용한 범위에서 반복성·필요성·위험도를 검토해 자동 동의·거부·보류를 선택 | 판단 근거 부족, 위임 범위 밖 정보·의무, 해석 충돌 |

세부 설계 원칙:

- ‘저장된 이름·전화번호를 요구한다’는 조건만으로 허용하지 않는다. 수집 항목, 목적, 실제 수신자와 제3자 제공 대상, 보관 기간, 필수/선택 여부를 구조화해 정책과 비교한다. 같은 기관에서도 내용이 바뀌면 다시 비교한다.
- 자동 처리는 **동의·거부·사용자 확인·해당 이벤트 건너뛰기**를 구분한다. 선택 동의가 정책 밖이면 거부하거나 미선택하며, 필수 동의를 허용할 수 없으면 사용자에게 묻거나 사용자가 정한 제외 정책에 따라 중단한다.
- 3단계의 ‘프로필에 없는 항목’ 허용은 새로운 개인정보나 경험을 만들어내라는 뜻이 아니다. 실제 값이 필요한 경우에는 사용자가 허용한 기존 정보 출처에서 확인할 수 있어야 하며, 없는 값은 질문한다.
- 반복 출현이나 모델의 ‘낮은 위험’ 평가만으로 권한을 넓히지 않는다. 사용자가 정한 허용 범위와 명시적 근거를 함께 만족해야 한다. 마케팅, 포괄적 제3자 공유, 결제·민감정보 등은 통상적인 경품 안내 동의와 별도 범주로 둔다.
- 허용 항목·목적·수신자 범주·최대 보관 기간·선택 동의 처리·판단 불확실 시 동작을 조정할 수 있게 한다. 설정 화면에는 각 단계의 실제 예와 적용 범위를 보여준다.
- 자동 결정에는 해당 안내문, 적용 정책 버전, 수신자/항목/기간, 처리 결과와 이유를 남긴다. 완료한 응모 상세에서 사람이 읽기 쉬운 동의 요약을 제공하고 원문은 펼쳐서 확인한다.
- 동의 자동화가 최종 제출 자동화를 켜지는 않는다. 정책 변경·철회는 진행 중 작업의 기존 허용을 무효화하고 새 범위를 확인한다. 이미 외부에 전송된 동의가 앱 설정 변경만으로 철회됐다고 표시하지 않는다.

검증에는 같은 통상 동의 재사용, 목적·수신자·보관 기간 변경, 필수/선택 혼합, 프로필 밖 항목의 근거 유무, 불명확한 문구와 악성 페이지 지시, 동의 거부·위임 철회를 포함한다. 성공률뿐 아니라 허용 범위 밖 자동 동의, 필요한 확인 누락, 불필요한 질문 횟수를 각각 측정한다.

## 11. 설계 근거

공식 문서는 변경될 수 있으므로 구현 직전에 다시 확인한다. 아래 사실은 기능의 현재 계정별 사용 가능 여부를 보장하지 않는다.

- [ChatGPT plan usage 개요](https://developers.openai.com/siwc/token-sharing-open-source): 오픈소스·로컬 앱이 별도 동의를 통해 적격 Responses 요청에 플랜을 사용할 수 있는 공식 경로.
- [ChatGPT 연동 제한](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations): 직접 HTTP 경로는 `store: false`, `stream: true`를 요구하며 일부 필드·호스팅 도구를 지원하지 않는다. 브라우저 실행과 작업 상태는 앱이 담당한다.
- [ChatGPT 연동 오류 복구](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery): 플랜 사용 권한을 확인하고, 한도·부적격·일시적 오류를 구분한다. 실제 결과로 접근을 검증한다.
- [ChatGPT API 크레딧 혜택](https://developers.openai.com/api/docs/guides/chatgpt-api-credits): 적격 구독의 별도 API 조직 연결 혜택이며, 앱의 OAuth 플랜 사용과 다른 경로다.

## 12. 후속 고도화: 응모로 추가한 팔로우·친구 정리

2026-11-11 사용자 피드백. **후속 개발 대상으로 기록하며 아직 구현·실행하지 않는다.** 네이버·인스타그램 등에서 응모 과제를 수행하며 새로 추가한 팔로우·이웃·친구 관계를 모아 두고, 결과 발표와 충분한 유예기간이 지난 뒤 대시보드에서 일괄 해제를 검토·실행할 수 있게 한다.

- 관계별로 플랫폼, 실행 계정, 대상 식별자/URL, 추가 전 상태, 실제 추가·검증 시각, 관련 이벤트/과제와 증거를 보존한다. 이미 있던 관계는 ‘기존 관계’로 구분해 정리 대상에서 제외한다. 과거 기록에서 추가 전 상태를 확인할 수 없으면 앱이 새로 만든 관계라고 추정하지 않는다.
- 같은 대상을 여러 이벤트가 요구하면 관계 하나에 해당 이벤트들을 연결한다. 모든 관련 행사의 유지 조건이 끝난 뒤에만 해제 후보로 올린다. 결과 발표일, 발표 확인 여부, 경품 수령·배송 진행 상태, 주최자의 팔로우 유지 조건과 사용자가 정한 유예기간을 함께 판단한다. 발표·유지 기한이 불명확하면 자동 해제하지 않고 보류 사유를 표시한다.
- 대시보드는 ‘유지 중 / 정리 가능 / 확인 필요 / 해제 완료’와 선정 이유를 보여준다. 사용자는 개별 제외·계속 유지·유예기간 변경·묶음 승인을 할 수 있어야 한다. 추후 자동 정리는 별도 명시적 위임으로 제공하며 기존 응모·게시 승인만으로 해제를 승인했다고 간주하지 않는다.
- 실행 직전에 실제 계정·대상·현재 관계 상태와 사용자의 유지 설정을 재확인한다. 이미 해제된 대상은 건너뛰고, 로그인·추가 인증·플랫폼 제한에는 중단/보류한다. 플랫폼별 해제 가능 범위를 별도로 검증한다.
- 일괄 처리의 일부 성공·실패·결과 미확인을 항목별로 기록한다. 결과가 불명확하면 현재 관계를 다시 읽고 판단하며, 재시도 때문에 다시 팔로우/친구 추가되는 토글 동작을 방지한다. 중단과 재개를 지원한다.

검증에는 기존 관계 보호, 여러 이벤트가 공유하는 대상, 발표 지연·당첨 후 수령 대기, 사용자 유지 지정, 계정 변경, 중복 실행, 일부 실패와 불명확한 해제 결과를 포함한다. 응모 접수, 당첨·수령, 관계 정리의 완료 상태는 각각 구분한다.
